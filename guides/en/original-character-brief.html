An AI Character OC Builder Brief That a Small Game Team Can Review

Written by the Wery AI brand team with AI assistance.

A character description can be detailed and still leave an artist unsure what to draw. “Quiet, resourceful, mysterious, with an elaborate coat” offers an atmosphere, but it does not explain what the player must recognize or what the character does in the first scene. Before using an AI character OC builder, a small game team can turn those adjectives into a brief with decisions someone can review.

This tutorial uses an invented character: a maintenance apprentice responsible for keeping a floating greenhouse running. The example is a planning document, not an account of generated artwork or a working game integration. The structured text below is a human handoff format. It is not a Wery API schema and should not be treated as an executable request.

Give the character a job inside one scene

Start with a scene in which the character must act. Our apprentice wants to repair a failing irrigation system before the greenhouse reaches a dry region. They also want to hide the fact that their earlier shortcut caused part of the problem. That tension creates a reason for their choices without deciding every later plot point.

Next, identify what the player should understand at first glance. The apprentice works with equipment, moves through narrow passages, and carries a small set of frequently used tools. Those requirements may influence silhouette, clothing and pose. They do not automatically require glowing symbols, complicated armor or a dozen unrelated accessories.

Keep story information and visual information connected but separate. A fear of disappointing a mentor may belong in the character note. It does not need to become a literal object on the costume. The visual brief should describe details that can actually be assessed in an image.

Write a small, explicit handoff document

The original character builder in Wery describes a workflow based on appearance, clothing, style, pose and setting, with the idea continued in the workspace. A team can prepare those inputs in its own document before asking for a visual direction.

For example, this YAML records decisions and open questions:

character:
  working_name: Greenhouse apprentice
  scene_goal: Restore water flow before the next stop
  conflict: Admit a shortcut or hide it and risk a larger failure
visual_brief:
  silhouette: Compact workwear with a clearly readable tool pouch
  pose: Checking a valve beside a narrow maintenance path
  preserve:
    - Practical clothing for climbing and reaching
    - One recognizable tool carried near the waist
  avoid:
    - Logos or recognizable existing characters
    - Tiny costume writing needed to understand the role
open_questions:
  - Should the tool look improvised or carefully maintained?
  - Is the first scene friendly or tense?

Each field is there because a collaborator can ask a useful question about it. Add a field only when it resolves a real ambiguity. An extensive form with empty answers can make the brief look complete while hiding the decision the team actually needs to make.

Turn the brief into an image request

Use ordinary sentences to connect the scene and visual requirements. For this example: “An original greenhouse maintenance apprentice checking a valve in a narrow floating greenhouse. Practical workwear, a readable tool pouch and a focused expression. Keep the silhouette clear. Explore a warm illustrated direction without copying an existing character or adding readable organizational branding.”

That request is deliberately narrower than a full character bible. It gives the image a task and a setting. The unresolved question about the tool can remain open until the team sees which interpretation supports the story. You do not need to settle every preference before asking for a first direction.

If the first direction does not communicate maintenance work, revise the pose or visible tool before adding more lore. More backstory will not necessarily make the image easier to understand. The next request should address the gap you observed, rather than restating the entire character description with stronger adjectives.

Review candidates against requirements, not novelty

Keep the brief beside the candidate. A surprising costume can be useful, but it still needs to fit the activity. Ask whether the apprentice could reach the valve, move through the passage and carry the chosen equipment in the depicted clothing.

Requirement Review question Possible follow-up
Role Does the character read as a maintenance worker? Clarify pose and visible tools
Silhouette Can the main shape be recognized at small size? Simplify secondary accessories
Scene Is the action understandable? Reduce competing background activity
Continuity Which features must stay in later images? Write a concise reference note
Story Does the image support the opening scene? Adjust expression or staging

Review identity details and anatomy as well as narrative fit. If the character will appear in several images, inspect each one separately. A written list of features helps communicate continuity goals; it is not a guarantee that every future image will preserve those details perfectly.

Commit the decision and leave the right questions open

For a repository-based team, place the selected brief next to the concept reference and a short decision note. Record why the direction was selected, what is still exploratory and who owns the next decision. Avoid calling a concept final production art if clothing, proportions or gameplay readability still need work.

Use clear headings when presenting the brief on a project page. The W3C guidance on headings is a useful reference for organizing that information. Put important requirements in readable text so they are available even when someone cannot inspect the image closely.

The handoff is ready when a collaborator can explain what the character wants, identify the visual requirements and locate the unresolved questions. Start with one scene and one brief. A small document that supports a decision will help the team more than a long character sheet nobody knows how to use.
